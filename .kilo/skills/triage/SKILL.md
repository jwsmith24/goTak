# Triage

Read `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md`. If absent, recommend `setup-engineering-workspace` and avoid guessing mutation commands or labels.

Canonical categories are `bug` and `enhancement`. Canonical states are `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, and `wontfix`. Treat conflicting state labels as a maintainer decision.

## Discover

Using read-only tracker operations, show unlabeled items, `needs-triage`, and `needs-info` items with new reporter activity, oldest first. Include merge requests only when repository configuration says they are a request surface.

## Evaluate one item

1. Read its body, discussion, labels, dates, and relevant diff. Read prior triage notes, repository instructions, domain docs, ADRs, and `.out-of-scope/` records.
2. Search by domain concept for an existing implementation and report where you looked.
3. Recommend one category and state with evidence; wait for maintainer direction.
4. Verify the claim safely. Reproduce a bug with `diagnosing-bugs` where proportionate. Review an attached diff without checking it out over the user's worktree. Report confirmed, contradicted, or insufficient evidence.
5. If decisions remain, invoke `grill-with-docs`. For `ready-for-agent` or `ready-for-human`, draft a brief using [AGENT-BRIEF.md](AGENT-BRIEF.md). For rejected enhancements, draft an `.out-of-scope/` update using [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md); never use it for already implemented behavior.

## Apply only after approval

Preview all comments, local files, labels, state changes, and closure separately. Every generated remote comment begins:

> *This was generated by AI during triage.*

Obtain explicit authorization for the exact mutation batch. Re-read tracker/local state immediately before applying and stop on material concurrent changes. Closure is consequential and must be explicitly included. Never assign work, alter code, merge, create branches, commit, or push as part of triage.
